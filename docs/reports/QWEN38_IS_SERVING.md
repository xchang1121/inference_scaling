# Qwen3.8-27B：IS 服务延迟与吞吐

当前性能入口只比较两阶段 IS 与同题 Base；此前的服务交付及并发记录单独列于后文。
配置与入口见 [SETTINGS.md](../SETTINGS.md)。固定块 IS 已退出真机性能对照。

## 两阶段 IS 与 Base（2026-11-02）

Qwen3.8-27B BF16、Ascend 910B3，MATH-500 的固定 4 道五级题，每题执行一次 Base 和一次 IS。
两组共享题目、根种子、采样策略和逐序列长度预算，执行顺序逐题交替；加载、预热、判题和题间缓存清空不计时。
IS 使用 `two_stage`、`selection_ready=true`、M=4、K=1、B=1024；其余参数沿用下述模型与引擎设置。
这是固定配置的短负载验证；运行代码为 `5c98b9a`，尚未包含后续 CPU 边界查找和并发取消修改。

两组各 4 对请求均成功结束，思考解析完整，无奖励回退或总生成长度耗尽；`low` 的 4096 思考预算仍按统一策略执行。
TP=2 的末轮复用完整 rollout，使前两题无需等到新候选全部完成；最慢题则实际完成了第二轮的 5 条新补全。
IS 搜索期间仅有一条已准入、未结束请求的累计时间分别为 4.00 s、1.73 s，主要成本并非单请求尾部空等。
这一指标是应用层请求区间统计，不表示 NPU 利用率。

TP=4 的 IS 总耗时较 TP=2 低 31.7%，Base 则低 36.2%，IS 相对 Base 的时延开销没有下降。
两组来自不同主机和容器基础环境；引擎源码提交相同，Transformers 分别为 5.5.4、5.14.1，安装的 vLLM
元数据版本分别为 0.23.0、0.26.0。输出轨迹及长度不同，因此这些跨组差异不构成单独改变 TP 的因果对照。

样本正确题数未下降，但 4 题不足以证明普遍质量持平；时延、质量和输出长度也受采样轨迹影响。
`selection_ready` 使用前缀估计提前选择，具有额外选择偏差，不能把这一结果视为与完整等待同分布的纯执行加速。
默认配置暂不切换。取消请求后的生成 token 计数只作下界；上表计算量取引擎执行位置（含填充及取消前工作）乘以 `2P`，
仅近似稠密层计算量。两组测试结束后均已释放所用设备。

```bash
python scripts/benchmark_is_gpu.py --settings settings/inference.json \
  --questions 4 --repeats 1 --effort low --max-tokens 8192 \
  --label qwen38-fast-is --output results/qwen38-fast-is.jsonl
```

运行前在同一设置文件中指定本机模型路径、TP、`exploration_schedule="two_stage"` 和 `selection_ready=true`；
不改动仓库默认长度。题目由设置中的 MATH-500 选择规则确定，测量记录包含完整生效设置和代码版本。

## 当前快速路径的 HTTP 交付

同一 TP=2 引擎、上述快速配置及 `low/8192`，串行调用前两题，无请求预热。客户端种子使用服务入口的固定派生规则，
与配对入口不同；该组仅验证交付和成本字段，不与前表相减计算加速。

| 题目 | 思考 TTFT | 最终内容 TTFT | 整题耗时 | 输出 token | 正确 |
| --- | ---: | ---: | ---: | ---: | --- |
| intermediate_algebra/1197 | 150.30 s | 154.77 s | 181.82 s | 4941 | 是 |
| counting_and_probability/870 | 38.63 s | 44.96 s | 62.06 s | 1506 | 是 |

两题共 243.88 s、6447 个最终输出 token，输出吞吐 26.43 token/s（每卡 13.22）。两题均完整结束。
取消使完整生成量未知，服务如实返回 `null`，不计算全部生成 TPS。思考只有选定后才交付，因此首轮完整奖励仍造成
38–150 s 的可见输出等待；两阶段减少后续更新次数，不消除首轮等待。

## 历史服务验证设置（2026-10-29）

使用 Qwen3.8-27B BF16，权重提交 `1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0`。
硬件为 64 GB Ascend 910B3，比较卡数与交付方式，不改变 IS 的候选选择。

- 固定条件 IS：M=4、K=1、B=1024，保留完整序列，等待全部必要补全；超发、配额提前停止和两阶段探索关闭。
- 温度 1、完整词表、默认 8 词惩罚；思考段 Consilience，top-5、奖励温度 2。
- 引擎保持原生 262144 上下文、异步调度、前缀缓存、分块预填充和 `FULL_DECODE_ONLY` 解码执行图。
- 短负载显式使用 `low`（4096 thinking tokens）及 8192 总生成上限；仓库默认 thinking 预算 131072 和总长 `null` 不变。
- MATH-500 的 `test/intermediate_algebra/1197.json`，根种子 `20260808`，每次服务重启后的首个请求，无请求预热。
  模型加载与编译不计入，首次请求的延迟初始化计入。

运行环境为 torch-npu 2.10.0.post4、CANN 9.1.0、驱动 26.1.1；vLLM 源码提交 `0fc695fc6d1d`，
vllm-ascend 为 `5cb98caaadef`，保留已有的异步 metadata 兼容修正。本轮未修改计算算子。

这是短负载服务路径对照，检验输出完整性及交付时间，尚不足以评价整体准确率、p95 稳定性或长预算性能。

## 历史输出交付对照

已固定思考前缀在每轮选择后交付；无工具的最终内容在续写时增量交付。候选生成、权重与选择规则不变。
工具调用在完整解析后交付。实现见[服务说明](../../src/inference_scaling/serve/README.md)和
[`SamplingScope.finish`](../../src/inference_scaling/arllm/scope.py)。

| 交付方式 | 首段思考时间 | 首段最终内容时间 | 整题耗时 | 输出 token | 输出 TPS | 判定 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 逐轮交付思考，最终内容整段交付 | 150.70 s | 360.70 s | 360.70 s | 4378 | 12.14 | 正确 |
| 逐轮交付思考，最终内容增量交付 | 150.69 s | 310.69 s | 337.21 s | 4382 | 12.99 | 正确 |

该样本运行 4 轮 IS。原来的整段缓冲接口需等到整题完成才发送文本，因此逐轮交付思考使首段可见输出提前约
210 秒（58.2%）。这一对照来自同一请求的首次思考交付与完成时刻，未另计一次完整缓冲运行。
交付时间提前不等于生成工作量减少或 TPS 提高。

第二次运行的最终内容在该请求完成前 26.52 秒开始交付。两次的思考文本哈希不同，因此整题耗时下降
6.51% 仅为观测差异，不能归因于流式交付。两次均完整结束且判定正确，质量证据仅限这一道题。
固定种子不保证不同批处理调度下逐字一致，参见 [vLLM 复现说明](https://docs.vllm.ai/en/latest/usage/reproducibility/)。
第二次生成总量为 24457 token（搜索 23398、最终续写 1059），全部生成 TPS 为 72.53；
前向位置 32050，估计计算量 1.724 PFLOPs。第一次的服务版本未返回完整请求级成本，不作计算量对比。

随后修正了 HTTP 事件等待：任一文本增量或推理完成事件就绪即处理，消除原先最长一个保活间隔的额外等待。
该修改通过已有 CPU 测试验证；以上两行仍为修正前的记录。

## 历史同题串行与并发

使用已修正的服务，选择 `test/intermediate_algebra/1197.json` 和 `test/counting_and_probability/870.json`。
每题种子由根种子、题目 ID 和重复编号固定派生；M/K/B、奖励与长度沿用上述设置。
在同一 TP=2 服务上先并发 2 题，再串行执行，无请求预热，后执行的串行组可复用已有缓存。

| 题目并发度 | 整批耗时 | 输出 TPS | 全部生成 TPS | 估计 PFLOPs | 正确 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 403.53 s | 12.02 | 74.07 | 2.054 | 2/2 |
| 2 | 365.09 s | 16.77 | 80.40 | 2.270 | 2/2 |

整批耗时减少 **9.5%**，全部生成吞吐增加 **8.5%**；输出吞吐增加 39.5%，但输出总量也从 4851 增至 6124 token，
因此后者包含长度变化。两组的全部生成量分别为 29891、29354 token，所有请求均完整结束且答案正确。

| 题目 | 单题耗时：串行 → 并发 | 思考 TTFT：串行 → 并发 | IS 轮数：串行 → 并发 |
| --- | ---: | ---: | ---: |
| intermediate_algebra/1197 | 341.65 → 365.09 s | 150.59 → 126.49 s | 3 → 4 |
| counting_and_probability/870 | 61.88 → 76.36 s | 40.02 → 53.56 s | 1 → 2 |

多题重叠提高了整批吞吐，单题完成时间则增加 6.9% 和 23.4%。同种子下轨迹仍发生变化，导致自然停止位置和轮数不同。
这是相同采样策略与逐序列预算下的短负载结果，不是逐 token 相同的执行回放；准确率证据为两道题，尚未覆盖默认长预算。

## 复现与指标

设置由 [`settings/inference.json`](../../settings/inference.json) 统一提供，服务启动时只按设备调整权重路径、
TP 和相应引擎选项。测量命令：

```bash
python scripts/benchmark_is_service.py --urls http://127.0.0.1:8000 \
  --dataset math500 --questions 1 --repeats 1 --warmup 0 --concurrency 1 --cards 2 \
  --effort low --max-tokens 8192 --deadline 900 \
  --label tp2-stream --output results/tp2-stream.jsonl
```

客户端的 TTFT 包含排队和 HTTP 开销，只计非空思考或内容；角色事件、保活消息、未选候选不计入。
输出 TPS 为最终保留 token 除以整批墙钟时间；全部生成 TPS 另计未选候选和补全。
请求级成本分别记录搜索和最终续写，FLOPs 使用 `2 × 参数量 × 前向 token 数` 近似。
缺失计数、取消或抢占时不将不完整成本当作零；失败和长度耗尽纳入汇总。

该阶段的 341 项 CPU 检查覆盖生成请求、增量与最终文本一致、成本归属和异常清理。当前回归已收紧至 246 项。

## 长序列边界解析

单 token 思考标记改用原生元组查找，减少逐 token 的 Python 循环。多 token 标记仍用原有路径；
采样、奖励与思考边界定义不变。2 万组随机边界与原实现一致，当前 246 项回归全部通过，无新增测试。
本机 CPU、同一非空思考段、每长度 15 次的中位耗时如下，仅衡量 `ThinkingParser.split`：

| 思考长度 | 原实现 / ms | 原生查找 / ms |
| --- | ---: | ---: |
| 4096 | 0.592 | 0.037 |
| 32768 | 4.740 | 0.343 |
| 131072 | 18.880 | 1.298 |

解析环节缩短约 13.8–16.0 倍；整题仍包含模型生成与其他处理，尚未测得由该修改单独产生的端到端加速。
该实现适用于任意单 token 边界，不依赖模型结构或设备算子。
