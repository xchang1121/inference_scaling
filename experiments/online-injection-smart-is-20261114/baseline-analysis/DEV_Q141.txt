## Why Multiple Lines Collapse onto One Line in the APT (Maximo Anywhere) Application

This is a **known behavior** of the Maximo Anywhere (APT) mobile application. When you enter a Description (or similar multi-line text field) with line breaks on the mobile device, the app correctly displays the text with its separate lines *within* the Anywhere interface. **Example from the IBM technote:**

| Entered (mobile) | Saved/Displayed (Desktop / .TXT) |
|---|---|
| `TESTLINE1` ↵ `TESTLINE2` ↵ `TESTLINE3` | `TESTLINE1 TESTLINE2 TESTLINE3` |

### What's happening technically
- The Anywhere app sends the text field as a single string over the sync protocol.
- The carriage-return / line-feed (`\r\n`) / newline characters that represent your hard line breaks are **stripped and substituted with a space** during the write to the database row (or during export to a flat file).
- Maximo Desktop and any file/CSV/TXT export then read a single contiguous string with no embedded line breaks, so everything renders on one line.

### What you can do

1. **Workaround at entry time:** If the downstream consumer (your .TXT report, CSV, etc.) requires separate lines, you can insert a delimiter that will survive the sync (e.g., a pipe `|`, a semicolon `;`, or a double-space pattern) and then post-process the .TXT file to convert that delimiter back into a real newline (`\n`).

2. **Post-processing script:** After the .TXT file is generated, run a small script (PowerShell, Python, awk, etc.) that splits on the delimiter you chose and writes a new line for each segment:

   ```powershell
   (Get-Content input.txt -Raw) -replace '\s\|\|\s', "`r`n" | Set-Content output.txt
   ```

4. **Check for an APAR / fix pack:** IBM occasionally addresses this in later fix packs. **Bottom line:** The APT/AnyWhere sync protocol does not preserve embedded line-break characters in free-text fields; it flattens them into spaces. Use a delimiter-and-post-process workaround, or enter/modify the text in Maximo Desktop where line breaks are stored natively.

## Why OCR Merges Multiple Lines Into One

The most common cause is that the OCR engine is **not detecting or inserting proper end-of-line characters** (CR/LF — hex `0D 0A` on Windows, or LF `0A` on Unix) between what it visually perceives as separate lines. Instead of a line break, it emits a space or nothing, causing all the text to flow onto a single line in your `.txt` output.

### Root Causes

1. **Insufficient vertical spacing in the source** – OCR engines determine a "new line" by measuring the gap between text baselines. If the line pitch in the scanned document is very tight (e.g., a dense table, a fixed-width report, or a scan with a small DPI), the engine's line-break threshold may not trigger.

2. **Low scan/image resolution** – At low DPI (below ~200–300), the pixel distance between lines shrinks, making it harder for the OCR's layout analysis to distinguish separate lines.

3. **Inconsistent or unusual fonts** – Fonts with variable line-height, or documents where a "line" is actually created by narrow spacers rather than true line breaks, can confuse the segmentation step.

4. **OCR profile / template mismatch** – Many OCR engines use a "line-height ratio" or "minimum gap" parameter. If your working profile was tuned for single-spaced 12-pt text and your document uses tighter spacing, lines will merge.

### What You Can Do

| Action | Detail |
|---|---|
| **Increase scan DPI** | Re-scan (or re-image) at 300–600 DPI so the vertical gap between lines is unambiguous in pixels. |
| **Adjust the line-break threshold** | In your OCR tool's recognition settings, look for options like *"minimum line gap," "line-height threshold,"* or *"paragraph sensitivity"* and lower the required gap so tighter spacing still triggers a break. |
| **Check / create a recognition template** | If your "APT application" supports layout templates or ZONE definitions, define explicit text zones with a specified line-height so the engine knows where each line should end. |
| **Post-process the `.txt` file** | If the merged line contains a known delimiter (e.g., a fixed column width, a tab, or a repeated character), you can split lines with a simple script (awk, Python `str.split()`, or a regex like splitting on `\t` or on a width boundary). |
| **Verify the actual bytes** | Open the `.txt` in a hex editor. If you see only spaces where a new line should be, the OCR never emitted `\r\n` or `\n`. If you do see `\n` (0x0A) but your viewer (e.g., Notepad on older Windows) isn't rendering the break, the viewer may need a full CRLF (`0D 0A`) pair. |
| **Try a different engine or profile** | Engines like Tesseract, ABBYY, or Adobe Acrobat have different heuristics; one may handle your particular layout better. |

### Quick Diagnostic

Open the output `.txt` in a hex viewer:

- **No `0D 0A` or `0A` between what should be lines** → the OCR engine's layout segmenter failed to identify a new line. Fix the image quality, DPI, or line-gap threshold as above.
- **`0A` is present but `0D` is missing** → some viewers (especially older Windows Notepad) expect CRLF (`0D 0A`). Open the file in Notepad → *File → Save As → Encoding → UTF-8* (or simply re-save it in Notepad) to normalize the line endings, or use a viewer that accepts bare LF.

In short, the OCR is treating your multi-line block as a single wrapped line because its line-break detector isn't seeing enough vertical separation (or the right newline bytes aren't being written). Adjusting image resolution, the line-gap parameter, or post-processing the output will resolve it.

## Why Detail Lines Are Collapsing onto One Line in Your .TXT Output

This is almost always a **record/line-delimiter configuration issue** in the flat-file or report-export definition that the APT application uses to generate the .TXT output.

### Root Cause

When the APT application writes detail (line-item) records to the .TXT file, it should insert a **carriage-return/line-feed (CRLF, `\r\n`)** sequence at the end of each detail row. If that terminator is missing, suppressed, or overwritten by a field-level delimiter (e.g., a comma or pipe with no line break), every detail row gets concatenated onto a single physical line:

```
LINE1|LINE2|LINE3|
```
instead of the expected:
```
LINE1
LINE2
LINE3
```

### What to Check / Fix

1. **Flat-File / Export Template Definition**
   - Open the output-definition (or report-writer layout) that drives the .TXT generation.
   - In the **detail section**, confirm that a *new-record* (or *repeat-line*) command is present after the column group. Some report writers call this "Next Line," "New Record," or "Record Terminator."
   - Verify the **record-end character** is set to CRLF (or LF on Unix/Unix-like hosts). A blank or single-space value will cause the collapse you're seeing.

2. **Column / Field Width Settings**
   - If a fixed-width column is too narrow, the writer may *wrap* the text onto the same line rather than emitting a new record. Ensure each detail field's width accommodates the longest expected value, or that the wrapping behaviour is set to "new record" instead of "same line."

3. **Delimiter / Tab-Separation Mode**
   - If the export is configured as *space-delimited* or *tab-delimited* on a **single logical record**, the application may be treating all detail rows as one record with multiple fields. Confirm the export type is set to **multi-record** (one physical line per detail row) rather than a single concatenated record.

4. **Character-Encoding / Line-Ending Override**
   - Some middleware or EDI translators strip or normalize CR/LF characters. If a translator or spool utility sits between the APT app and the final .TXT, check its **end-of-record** setting (the issue is analogous to what IBM documents for missing CR/LF at the end of XML transactions—multiple records appearing on one line with no EOL character).

5. **Spool / Print vs. Flat-File Route**
   - If the .TXT is produced via a **print/spool route** rather than a true flat-file writer, the "line feed" may be suppressed. Switch the output destination to a flat-file writer node, or add an explicit `/* NEWLINE */` (or equivalent) control in the prologue of the detail group.

### Quick Verification

After making the change, generate a small test file and open it in a hex editor (or `od -c` / `xxd`). You should see `0x0A` (LF) or `0x0D 0x0A` (CRLF) at the end of every detail line. If those bytes are absent, the delimiter fix has not taken effect.

### Summary

The APT application is not "breaking" the data—it is faithfully writing every detail row **without a line terminator** because the export/report definition is missing (or has overwritten) the record-end (CRLF) command in its detail section. Add or restore the new-record/line-feed directive in that detail group, and each line will appear on its own row in the .TXT file.
