## Parascript Postal Database – Clarification

**The postal database is NOT a separate component.** It is a built-in feature of Parascript itself. You do not need to download or install anything additional. The FieldScript/Taskmaster guide you followed simply shows the *actions* (commands) used to invoke it, while the database file itself is something **you build and supply**.

### Why Your Values Are Being Overridden

The most common mistake is treating the postal database as if you were assigning values to a single field one at a time. Each assignment replaces the previous value, so only the last entry survives. A postal database is a **reference file** (plain text, one entry per line), not a field you accumulate into.

### How to Create the Postal Database

1. Create a plain-text file (e.g., `postalDB.txt`) containing valid postal codes, one per line:
   ```
   10001
   10002
   10010
   …
   ```
2. In your FieldScript (or Parascript UI under the OCR/Zone settings), point the **Postal Code Database** option to that file. In FieldScript this is typically done with an action like:
   ```
   PostalDB = "C:\YourFolder\postalDB.txt"
   ```
   (exact variable/action name may differ slightly by Parascript version – check the field list in the Parascript documentation for "postal" or "postcode".)
3. Assign the zone/field type as **Postal Code** (not free text) so Parascript actually consults the database during recognition.

### How to Access / Reference It in Taskmaster FieldScript

You do not "query" the postal database row-by-row in your script. You simply:

- Point Parascript to the file (step 2 above).
- Mark the relevant zone as a postal-code zone.

Parascript then uses the list internally to **constrain and correct** the recognized characters. You read the final recognized value from the zone as you would any other field.

### Does This Improve Recognition?

Yes, but in a **narrow** way:

- It constrains each character position to digits that appear in known postal codes, which reduces misreads (e.g., confusing "0" with "O" or "1" with "I").
- It can correct a single-character error if the result is close to a valid entry in the database (edit-distance correction).
- It does **not** improve recognition for non-postal fields, and if your source postal codes are not in the database, Parascript will flag the value as invalid rather than guessing.

So it is most effective when you have a **comprehensive, accurate** list of the codes actually appearing in your document set.

### Quick Checklist

| Item | Action |
|---|---|
| Postal DB installed separately? | **No** – it is a built-in feature. |
| File format | Plain text, one postal code per line. |
| Values overwritten? | You are writing to a field instead of building the file. Build the file first, then reference it. |
| Zone type | Set to *Postal Code*, not *Character* or *String*. |
| Recognition benefit | Improves digit-only postal fields; no effect on other zones. |

If after creating the file and setting the zone type the values still appear blank or wrong, double-check that the path in the FieldScript contains no spaces or special characters, and that the file encoding is plain ASCII (no BOM, no UTF-16).

# Parascript Postal Database & Vocabulary Issues

## Why Multiple Values Are Being Overridden in Your Vocabulary File

This is almost certainly a **file-format issue**. In Parascript, a vocabulary (or "character set"/"value set") file must have **one distinct value per line**:

```
10001
10002
10115
11201
```

If you placed several values on the same line (e.g., `10001 10002 10115`) or used commas, Parascript reads the entire line as a single token, so later entries visually "override" earlier ones. Also make sure:

- The file uses **CRLF or LF** line endings (no BOM, no tabs).
- The file is encoded as **plain ASCII / ANSI** (not UTF-16).
- The file extension matches what your FieldScript references (`.lst`, `.vab`, etc.).
- You are not mixing a *list* vocabulary with a *regular-expression* vocabulary in the same field definition; they use different file formats.

Fix the line breaks and re-load the vocabulary in Taskmaster; the overriding should stop.

## Is the "Postal Database" a Separate Install?

**No.** There is no standalone "Postal Database" product you download and install alongside Parascript. What the guide calls a *postal database* is simply **an external data file or relational-table lookup** that your Taskmaster rules use to **validate** a recognized field (typically the ZIP/ZIP+4 or the full delivery address). It is wired in through the normal Taskmaster data-connection mechanism:

1. **Create / obtain the data source.** This can be:
   - A flat file (CSV, fixed-width) of valid ZIP codes or DPB (Delivery Point Barcode) values.
   - A table in Oracle, SQL Server, MySQL, etc.
   - A network database maintained by your postal / carrier organization.

2. **Register it as a Data Source in Taskmaster.**
   In the Taskmaster Administrator, under *Data Sources*, add a connection (ODBC/JDBC/flat-file) pointing at that table or file. You are not installing anything new—just configuring a connection string.

3. **Reference it in a Rule (not in a FieldScript "action").**
   In the Taskmaster rule set, add a **Validate** or **Data Lookup** step on the ZIP field:
   ```
   If field "zip4" is NOT FOUND IN table USPS_ZIP (column ZIP_CODE)
       THEN set quality flag "ZIP_INVALID"
   ```
   The guide's mention of "actions" refers to the Taskmaster quality/annotation actions that fire based on that lookup result. The lookup itself is a data-source operation, which is why the guide doesn't show a FieldScript action for it—FieldScript handles *extraction and field-to-field logic*; cross-reference validation against an external table is a Taskmaster rule feature.

4. **If you need the lookup inside FieldScript** (e.g., a quick parity check), you can open the flat file from FieldScript:
   ```javascript
   // Pseudo – actual API name varies by Parascript version
   var db = data.open("zip_lookup.txt");   // or data.connect("jdbc:…")
   if (!db.find(row.zip4)) {
       field.setResult("REVIEW", "Unknown ZIP");
   }
   ```
   But for a production postal workflow the Taskmaster rule-based lookup is the standard approach.

## Does Parascript (FieldScript + Taskmaster) Actually Improve Recognition?

Short answer: **yes, but indirectly.** The underlying OCR engine (ABBYY, ReadOCR/Nuance, etc.) performs the raw pixel-to-character conversion. Parascript/FieldScript improves *effective* accuracy by:

- **Constraining the search space** – vocabulary files, character sets, and parity (e.g., "this field is 5 digits, max 4 9s") stop the engine from hallucinating characters that are not in the allowed set.
- **Post-processing logic** – FieldScript can normalize, trim, correct transpositions, apply Luhn checks on account numbers, and route ambiguous fields to human review.
- **Validation against trusted data** – the postal/ZIP/DPB lookup catches OCR errors that the engine itself cannot flag.
- **Training & retraining** – Parascript lets you save low-confidence images, correct them, and re-run the job with updated language models.

So Parascript does not make the OCR engine "see" better, but it dramatically reduces *unattended error rates* by layering constraints and validation on top of the raw recognition.

## Quick-Start Checklist

| Step | What to do |
|------|-----------|
| 1 | Fix the vocabulary file: one value per line, ASCII, no BOM. |
| 2 | Decide where your valid postal data lives (flat file vs. SQL table). |
| 3 | In Taskmaster Administrator → Data Sources, add the connection. |
| 4 | In the rule set, add a Validate / Lookup step on the ZIP (or address) field. |
| 5 | Add a Taskmaster *action* (flag, reject, or route-to-operator) that fires when the lookup fails. |
| 6 | Test end-to-end with a batch of known-good and known-bad images to confirm the override issue is gone and the postal validation catches errors. |

If after fixing the line-breaks the values still override, open the Parascript/FieldScript log (usually `parascript.log` in the install `logs` folder) and search for `vocab` or `value set` warnings—that will tell you exactly which line the parser is choking on.

# Parascript Postal Database & Vocabulary File Issues

## Is the Postal Database a Separate Component?

**No.** The postal database in Parascript is **not** a separate product or standalone installation. It is implemented as a **simple text file** (a list of valid postal codes, one per line) that you reference from your FieldScript vocabulary or field definition. The guide you followed only mentions "actions" because the postal validation is an *implicit* behavior triggered when you tag a field as postal-aware — there is no extra installer or service to deploy.

### How to create and use it

1. **Create the file** – e.g. `C:\Parascript\DB\postal_us.txt`
   ```
   10001
   10002
   10003
   ...
   ```
   Plain ASCII/UTF-8 (no BOM), **one code per line**, no leading/trailing spaces.

2. **Reference it in your vocabulary or field definition:**
   In your vocabulary file, add a section or in the field definition in Taskmaster:
   ```
   field zone postal
       name "ZIP_CODE"
       substitutes
       postal "C:\\Parascript\\DB\\postal_us.txt"
   end
   ```
   Or, within the vocabulary file itself, use the `postal` keyword to point to the database file so that any field tied to that vocabulary gets postal-code validation/completion automatically.

3. **Access at runtime** – Parascript loads the file via the path you specified. There is no API call; the engine reads it when the postal field is evaluated. You can verify it is being picked up by checking the recognition detail / audit screen in Taskmaster, which will show a "postal match" or "postal completion" event.

## Why Multiple Values Are Being Overwritten in Your Vocabulary File

This is the more common pitfall. Check the following:

| Symptom | Likely Cause | Fix |
|---|---|---|
| Only the **last** line is recognized | File saved with only `\n` and no `\r\n`, or opened in a tool that collapses lines | Re-save as **DOS/Windows CRLF** line endings |
| Only one "entry" appears | Multiple values accidentally placed on **one line** separated by commas/spaces | Ensure **one token per line**, no delimiters |
| File appears empty in Taskmaster | Wrong absolute path, or path contains spaces without quotes | Use forward slashes or escape; verify the file is actually at that path on the server/worker |
| Overridden on every scan | The vocabulary file is in a temp/output directory that gets wiped between runs | Move it to a **persistent** directory (e.g., `C:\Parascript\shared\vocab\`) and reference that |

# Parascript Postal "Database" – What It Actually Is and How to Fix Your Issue

## It Is Not a Separate Component

There is no separate "postal database" product or installable package. In Parascript FieldScript the so-called *postal database* is simply a **pick-list text file** that you create yourself and then **bind to a field via a `List` action** in your Table Definition (TDL) / FieldScript rules. The guide mentions "actions" because that is exactly the mechanism: an action tells the engine *"validate/correct this field against this list."*

## Why Your Values Are Being "Overridden"

The most common causes:

| Symptom | Typical cause |
|---|---|
| Only the **last** postal code survives | The pick-list file has all values on **one line**, or there is a single field whose `List` action is applied sequentially and each iteration replaces the previous result. |
| Values disappear after a save | The file uses a wrong encoding (UTF-16, BOM) or Windows/Unix line-ending mix, so Taskmaster reads it as one record. |
| Multiple fields share one list and step on each other | Two field rules reference the **same** pick-list name but are meant to be independent. |

### Correct pick-list format

Create a plain-text file (e.g. `zipcodes.txt`):

```
01001
01002
01003
…
99501
```

* One postal code **per line**.
* No trailing spaces, no header line, no separators.
* ASCII / ANSI encoding, LF or CRLF line endings.
* Keep the file in the project's `Lists` (or `PickLists`) folder so the TDL can resolve the path.

## How to Wire It Up (the "action" the guide refers to)

1. **In the Table Definition (TDL / XML schema)** define the field, e.g.

```xml
<Field name="ZipCode" type="string" lemma="zip">
  <Rule>
    <Action name="List" file="Lists\zipcodes.txt" mode="correct"/>
  </Rule>
</Field>
```

2. **In the FieldScript / recognition rules** (depending on your Taskmaster version) you may see it expressed as:

```
FIELD "ZipCode"
  LIST "Lists\zipcodes.txt"
  ACTION CORRECT
END
```

   * `mode="correct"` (or `CORRECT`) means: if the OCR engine produced something that doesn't match, snap it to the **closest** entry in the list.
   * `mode="validate"` (or `VALIDATE`) means: mark the field as bad if no match is found, but leave the raw value.

3. **For multiple postal fields** (e.g. a "From" zip and a "To" zip), give each field its **own** `List` action entry (they may point to the same file, but they must be separate rule blocks). This is the usual reason people see "overriding" – two fields are sharing one rule block.

## Does Parascript Actually Improve Recognition?

Yes, but understand the role:

* Parascript is a **post-OCR interpretation layer**, not the OCR engine itself. The scan engine (e.g. Kofax Capture, VRS, ABBYY, or whatever you feed into Taskmaster) does the pixel-to-text step.
* Parascript then applies **context, grammar, and pick-list constraints** to that raw text. A partial or ambiguous "9150I" becomes "91501" because the zip list says so. A misread city name snaps to the correct entry from the city pick-list.
* Real-world gains are most visible on **structured, repetitive documents** (invoices, mail, forms) where field positions and legal-value sets are known. For free text with no constraints, the improvement is minimal.
* It also handles **cross-field logic** (e.g. zip must match the state pick-list), confidence-based acceptance/rejection, and routing – things a raw OCR engine cannot do.

## Quick Checklist to Unblock You

1. Export your current pick-list file; open it in a hex editor. Confirm **one value per line, `\r\n` or `\n`, no BOM**.
2. Ensure each postal field has its **own** `List` action rule, not a shared block.
3. Set the action to `CORRECT` (not just `VALIDATE`) if you want the engine to **fix** the value rather than only flag it.
4. After editing the TDL/FieldScript, **re-build / re-import** the project in Taskmaster so the change takes effect (a simple save sometimes is not enough).
5. Run a single test page and look at the **recognition report / annotations** to see which postal codes were accepted vs. corrected.
