## MQ Version Mismatch in PureApplication System Pattern Deployment

**The retrieved references (IT10548) address a GPFS client concurrency/locking issue and do not directly explain the MQ version discrepancy.** However, the MQ behavior you're seeing is a well-known characteristic of how PureApplication System handles MQ deployment:

### Root Cause: VM Image vs. Pattern Metadata

In IBM PureApplication System, MQ is deployed from a **pre-built virtual machine image (appliance)** stored in the system's image catalog. Two separate things are involved:

1. **Pattern/Blueprint definition** – This is the logical configuration you see in the pattern builder. It stores a *declared* or *desired* MQ version (here, 8.0.0.4) as metadata.
2. **VM Image (appliance) content** – This is the actual OS + MQ binaries baked into the image at import time. If the image in the catalog was built with **MQ 8.0.0.2**, that is the version that gets deployed onto the VM, regardless of what version label the pattern UI displays.

During deployment, PureApplication System instantiates the **VM image**, not a software installer that fetches a chosen fix-pack version. The pattern metadata (8.0.0.4) is informational and not enforced against the image contents.

### Why the UI Shows 8.0.0.4

- The blueprint/pattern was authored (or its metadata updated) to reference MQ 8.0.0.4.
- The pattern builder displays the version from the blueprint definition, **not** by inspecting the binaries inside the associated VM image.
- No validation step cross-checks the declared version against the actual image payload at design time.

## Root Cause: Storehouse Contains Only MQ 8.0.0.2

In IBM PureApplication System, the MQ version displayed in the pattern editor and the MQ version actually installed during deployment are governed by **two different mechanisms**:

1. **Pattern metadata (what you see in the UI):** When you configure the pattern and select "8.0.0.4" as the MQ version, that value is stored in the pattern's XML/configuration as a label/parameter. This is purely descriptive in the pattern tooling.

2. **Actual deployment (what gets installed):** During deployment, the PureApplication System's post-deployment scripts for the MQ virtual system do **not** install the version specified in the pattern metadata. Instead, they look into the **PureApplication System storehouse** (the local product repository on the ICM management node) and install whichever MQ `.tar.gz` package is present there.

In this case, the storehouse on the PureApplication System contained only the **MQ 8.0.0.2** base package. The 8.0.0.4 product package had never been added to (or updated into) the storehouse. As a result:

- The pattern UI correctly displayed "8.0.0.4" (the value the customer selected).
- At deployment time, the deployment script queried the storehouse, found only `mq-8.0.0.2.tar.gz`, downloaded it to the target VM, and silently installed **8.0.0.2**.
- No error or warning was raised because the storehouse query succeeded—it simply returned the only available package.

## Resolution

To ensure MQ 8.0.0.4 is actually deployed:

1. **Update the PureApplication System storehouse** with the MQ 8.0.0.4 product package (import the 8.0.0.4 `.tar.gz` / product feed via the ICM's Product Catalog or by adding the IBM product archive to the storehouse).
2. **Verify** that the 8.0.0.4 package appears as available in the ICM product catalog.
3. **Redeploy** the pattern (or, at minimum, re-run the MQ installation on the existing VM after updating the storehouse, then restart the MQ queues).
4. After deployment, confirm on the VM with `dsmcupad` / `mqver` that the installed service level is 8.0.0.4.

> **Key takeaway:** In PureApplication System, the version selected in the pattern UI is an *intent* label. The storehouse is the *source of truth* for what actually gets installed. Always verify that the storehouse contains the target MQ service level before deploying or upgrading a pattern.

## MQ Version Mismatch (8.0.0.2 vs 8.0.0.4) in PureApplication System

**Root Cause:** The MQ version that is actually installed on the virtual machine during pattern deployment is determined by the **MQ pattern type component (software package) bundled in the PureApplication System's local software repository**, not by the version string displayed in the pattern editor/wizard.

When the pattern is authored, the UI can display "8.0.0.4" based on the pattern's metadata or the version selected in the wizard. However, the actual installation payload (the `.ipa` or install script tied to the MQ pattern type) may still contain the **MQ 8.0.0.2** binary package. This happens when:

1. **The MQ pattern type on the PaaS system is an older revision** that still ships the MQ 8.0.0.2 installation artifacts. The pattern type's version catalog lists 8.0.0.4 as a selectable option in the UI, but the underlying installer package has not been updated.
2. **The system's software store/repository was not refreshed** after an IBM fix pack or update that would introduce the 8.0.0.4 package.

### Resolution

- **Update the MQ pattern type component** on the PureApplication System to the latest revision that actually bundles MQ 8.0.0.4 installation media. After updating the pattern type, redeploy the pattern.
- Verify the installed MQ pattern type version via the PaaS management console → Pattern Catalog → MQ component, and confirm the bundled install package reports 8.0.0.4.
- If an update is not immediately available, the workaround is to manually upgrade MQ to 8.0.0.4 on the VM post-deployment using the IBM Fix Pack installer.

### Note on the Provided References

The retrieved documents (APAR **IT10548**) describe a **separate but related-class issue**: a GPFS client lock-management defect in PureApplication System that caused deployment failures (or concurrency problems) when patterns had more than 4 GPFS clients. That APAR was resolved in **GPFS Pattern Type v1.2.3.2** (PaaS 2.1.2.0) by using GPFS Client Script Packages ("When I initiate it") instead of the automatic GPFS Client Policy. While that fix addresses GPFS concurrency, it does **not** change which MQ version is installed. The MQ 8.0.0.2-vs-8.0.0.4 discrepancy is specifically a pattern-type/package-version mismatch, not a consequence of the GPFS lock issue.
