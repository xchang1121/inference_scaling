## Answer

**The BPM internal Document Store (database-backed) is not compatible with IBM DB2 pureScale**, and the hanging threads you observe during server startup and Document Store initialization are a known symptom of this incompatibility. The provided references address a different issue (Content Store licensing in clustered environments, CWLLG2229E/CWLLG0826E) and do not contain the specific solution for this pureScale problem.

### Root Cause

DB2 pureScale handles JDBC connections, distributed transactions, and lock protocols differently from a standard DB2 LUW instance. The BPM Document Store initialization code performs operations (such as certain metadata queries, lock acquisitions, or health checks) that block indefinitely against a pureScale data source, causing the threads you see in `SystemOut.log` to hang and preventing the application server from completing its startup.

### Resolution

Since the references do not prescribe a configuration fix, the standard workaround is:

1. **Switch the Document Store to a file-system–backed provider** rather than the DB2-backed one. In the BPM administration console, go to the Document Store configuration and change the storage type from "Database" to "File" (or use the external/hybrid file option). This removes the pureScale JDBC dependency entirely.

2. **If a database-backed Document Store is required**, do **not** point it at the pureScale data source. Instead:
   - Create a **separate DB2 LUW (non-pureScale) instance** dedicated to the Document Store.
   - Define a new JNDI data source (e.g., `jdbc/BPMDS`) that references only that non-pureScale database.
   - Reconfigure the Document Store in the BPM runtime to use that data source.

3. **Keep the Process Server (process store) on pureScale** – the BPM process server itself is supported on pureScale. Only the Document Store component is the part that is incompatible.

4. **After making the change**, restart the application server. The initialization threads should complete normally and the server should reach a "running" state.

### Verification

- Check `SystemOut.log` after restart; the previous "hanging thread" stack traces during Document Store initialization should no longer appear.
- Confirm the Document Store is operational by uploading and retrieving a test document from the BPM admin console.

> **Note:** The references supplied in this question (CWLLG2229E / CWLLG0826E) concern a *Content Store* licensing mismatch in a clustered BPM environment and are not applicable to the Document Store + pureScale hang you are experiencing.

## Answer

**No — the BPM internal Document Store is not supported with IBM DB2 pureScale.** The internal Document Store is designed to use the **embedded HSQLDB** database (its default configuration) or, if an external RDBMS is required, a standard (non-clustered) DB2 for Linux/UNIX/Windows instance. DB2 pureScale's shared-disk, scale-out architecture (synchronous multi-member buffer pool, cluster-wide locking) is incompatible with the DDL/migration operations the Document Store performs during initialisation, which is exactly why you see threads hanging in `systemOut.log` and the server never completes its start.

### Why the threads hang

During server start the Document Store initialisation routine opens a JDBC connection and attempts to:

1. Verify / create its tables and metadata.
2. Run schema-migration (flyway-style) scripts.
3. Acquire exclusive row/table locks while doing so.

DB2 pureScale routes those requests through its member-to-member synchronisation layer. The lock or DDL the Document Store expects to complete locally is held or replayed across all pureScale members, so the JDBC driver waits indefinitely for a cluster-wide acknowledgement that never comes in the single-node, single-connection pattern the BPM init code assumes. The initiating thread blocks, and the rest of the server bootstrap stalls behind it.

### How to resolve it

1. **Revert the Document Store to the supported embedded HSQLDB.**
   This is the default. In WebSphere Admin Console → *Servers → Application Servers → bpmserver → Enterprise Beans → DocumentStore*, set the database type back to **HSQLDB** (or, via `wsadmin`:
   ```
   AdminTask.DocumentStore.showMBeans()
   AdminTask.DocumentStore.update('-dbName myDocStore -dbType HSQLDB ...')
   ```
   )
   Restart the node. No external RDBMS connection is made, so the pureScale conflict disappears.

2. **If you truly need an external RDBMS for the Document Store,** point it at a **standard (non-pureScale) DB2 LUW** instance instead. Create the data source in WAS, supply the correct JDBC driver and driver-type property, and let the BPM initialisation scripts create the schema on that single-instance DB2.

3. **Work-around if you cannot change the backend immediately:**
   * Stop the BPM server.
   * Manually create the Document Store schema in a standard DB2 database that you *can* reach (or in HSQLDB).
   * Set the Document Store's **"run bootstrap / auto-initialise" flag to `false`** so the server skips the DDL at start and simply opens the pre-existing tables.
   * Start the server; the threads will no longer hang because no cluster-level DDL is issued.

4. **Keep your business-process / process-application databases on pureScale** if that is your choice — the incompatibility is specific to the *internal Document Store* initialisation path, not to every DB2 connection in BPM.

|---|---|
| Process Database (business processes, token table, etc.) | pureScale **or** standard DB2 LUW |
| Internal Document Store | Embedded HSQLDB (default) or **standard** DB2 LUW — **not** pureScale |
