ANSWER
## Root Cause

Both **EJPDB0085W** and **EJPFD0016E** are symptoms of the same underlying problem shown by **EJPDB0166W**: your external Oracle database has its character set set to **WE8MSWIN1252**, but WebSphere Portal 8.5 mandates a UTF-8–family encoding. The Portal data-store sanity check (`DataStoreServiceImpl.checkCorrectSetup`) finds that the `NLS_CHARACTERSET` parameter under `[NLS_DATABASE_PARAMETERS]` is not one of the accepted values **UTF8, AL16UTF16, AL32UTF8, or UTFE**, so it aborts initialization (→ EJPFD0016E).

## Resolution

The external Oracle instance must be rebuilt (or its character set changed) to use a UTF-8–family character set, then the Portal schema data re-loaded.

### Option A – Recreate the Oracle database with UTF8 (recommended)

1. **Create a new Oracle PDB/CDB or instance** using DBCA (or the equivalent `create database` script) with:

   ```
   CHARACTER SET  = UTF8          (or AL32UTF8)
   NATIONAL CHARACTER SET = AL16UTF16
   ```

   Verify after creation:

   ```sql
   SELECT parameter, value
   FROM   nls_database_parameters
   WHERE  parameter IN ('NLS_CHARACTERSET','NLS_NCHAR_CHARACTERSET');
   -- NLS_CHARACTERSET must return UTF8 (or AL16UTF16 / AL32UTF8 / UTFE)
   ```

2. **Restore / import the Portal schema data** (JCR, ICDB, VMDB, IBSSDB, WAADB, etc.) from the export you took before the transfer, using `impdp`/`expdp` (Data Pump) or `sqlplus` SQL\*Loader. Data Pump in 12c+ performs implicit character-set conversion, so the previous WE8MSWIN1252 data will be converted to UTF8 on load.

3. **Associate the Portal database in the administrative console** (or `ManageRegistryProcess` if the migration was done that way) pointing to the new UTF8 instance.

### Option B – In-place character-set conversion (only if the DB is still empty or you accept downtime)

If the data has already been loaded into the WE8MSWIN1252 instance and you cannot recreate it:

```sql
SHUTDOWN IMMEDIATE;
STARTUP MOUNT EXCLUSIVE;
ALTER DATABASE CHARACTER SET UTF8 EXTENDED;   -- 12c+ only
ALTER DATABASE OPEN;
```

> **Caveat:** `EXTENDED` is required when data already exists. Oracle will validate every row; validation can take a long time and will fail if any existing data cannot be represented in UTF8. This is riskier than Option A and is not the approach IBM documents for this error.

### Post-fix verification

After the character set is corrected and data re-loaded:

1. Restart the Portal node (or the entire node if it was in a failed-init state).
2. Confirm in `SystemOut.log` that **EJPDB0085W**, **EJPDB0166W**, **EJPDB0160E**, and **EJPFD0016E** no longer appear.
3. Open the Portal page (`/wps/portal`) and verify content, search, and composite applications render correctly.
4. Optionally run the Portal data-store integrity check via the administrative console under **System → ManagePortal** to confirm the JCR domain is healthy.

## Why this happened

During the external-DB transfer the target Oracle instance was (re)created with the OS-default character set (WE8MSWIN1252 = Windows-1252/ISO-8859-1) rather than explicitly specifying `UTF8`. Portal 8.5 hard-fails at startup if the JCR (and by extension the other Portal) databases do not report an accepted UTF-8-family `NLS_CHARACTERSET`, which is exactly what the stack trace in `DataStoreServiceImpl.checkCorrectSetup` → `init` shows. Correcting the character set to **UTF8** (or AL32UTF8) and re-loading the data resolves both EJPDB0085W and the downstream EJPFD0016E initialization failure.
