## Cause of DataType Corruption After Impact 7.1.0.11 Cluster Failover/Failback

### Root Cause

In Impact 7.1.0.11, the cluster node-to-node synchronization of `.type` files does not correctly replicate all nested/structured properties. The property in question, **`*.SQL.USERPARAMETERS`**, is a multi-line, structured sub-property that enumerates every target-table field (and its associated parameter/property bindings) for the DataType's parameterized SQL query. During a failover or failback event, the file-level copy of the DataType definition between the active and standby ImpactServer nodes **drops or truncates this property**, leaving the remainder of the `.type` file intact but the SQL parameter block absent. Without `USERPARAMETERS`, the DataType's query has no field mapping, so the server treats the definition as empty/corrupt and the GUI cannot render or load the DataType at all.

### Why `USERPARAMETERS` Specifically?

- It is the **most complex** sub-property in a DataType file, containing a repeating block per target field (field name, data type, source property/parameter, transformation).
- The 7.1.0.11 replication routine serializes the DataType to the standby node as a flat key-value set; certain structured values that span multiple sub-keys (as `USERPARAMETERS` does with its per-field child entries) are **not fully reassembled** when the standby node becomes active after a failover/failback cycle.
- Simpler scalar properties (e.g., `SQL.QUERY`, `SQL.DATASOURCE`) survive the copy intact, which is why the DataType is not wholly blank but specifically loses its parameter-to-field mapping.

### Confirmation

Compare the `.type` files on disk (located under the ImpactServer data directory) taken **immediately before** and **after** a failover. The only diff on the affected DataTypes will be the missing `USERPARAMETERS` block:

