# MQ Version Discrepancy in PureApplication System Pattern Deployment

- The **PureSystem Storehouse** can correctly contain and list **both** `mq-8.0.0.4.tar.gz` **and** `mq-8.0.0.2.tar.gz` as available MQ virtual products. The pattern editor and library therefore display 8.0.0.4 accurately.


The mismatch is **not** a configuration error in the pattern. # Clearing "Errors Found" in `crm_mon`

When `crm_mon` reports failed resource actions (e.g., a resource start/stop that returned a non-zero return code), the failure is recorded as a *sticky* error in the cluster's resource-state memory. The cluster will not retry the failed operation until the error is explicitly cleared.

## The Command

Use `crm_resource` with the **`-C`** (clear) flag:

```bash
# Clear a specific failed action on a specific host
crm_resource -r <resource_name> -H <hostname> -C

# Clear failures for a resource on all hosts
crm_resource -r <resource_name> -C
```

### Example

If `crm_mon -1` shows:

```
Failed Actions:
  drbd_exphome_device_start_0 (node=netezza_h2, call=15, rc=1): Error
```

Run:

```bash
# crm_resource -r drbd_exphome_device -H netezza_h2 -C
```

After clearing, re-check with:

```bash
# crm_mon -1
```

The "Failed Actions" / "Errors Found" section should now be empty.

## Important Notes

| Consideration | Detail |
|---|---|
| **Diagnose first** | Before clearing, check *why* the action failed: `crm_resource -r <res> -O` (operation history) and review logs (`/var/log/messages`, `systemctl status <res>`). |
| **Root / proper user required** | Must be run as `root` or a user authorized for CRM operations. |
| **Sticky failure** | Without `-C`, the cluster keeps the failure and will **not** re-attempt the operation. Clearing resets that flag so the cluster can retry. |
| **Node-level errors** | If the error is tied to a *node* (e.g., a lost node), use `crm_node -e <node_name>` to un-fence/clear the node entry, then verify with `crm_mon -1`. |
| **Post-clear** | If the underlying problem (misconfiguration, hardware fault, etc.) is still present, the resource will simply fail again in the next cycle. Fix the root cause before or after clearing. |
| **Long options** | For readability, the long form works identically: `crm_resource --resource <res> --host <host> --clear`. |

## Quick Verification Loop

```bash
# 1. See the error
crm_mon -1

# 2. (Optional) Inspect the failure details
crm_resource -r <resource_name> -O

# 3. Clear the sticky error
crm_resource -r <resource_name> -H <hostname> -C

# 4. Confirm it's gone
crm_mon -1
```

This is the standard procedure across Pacemaker / CRM-based clusters (including IBM Netezza / PureData environments that bundle `crm_mon` and `crm_resource`).

# Content Engine System Health Page – Fixed Content Advice & Storage Area Showing "Unavailable"

## Root Cause

The **System Health** page (typically the Content Engine admin/monitoring console) reflects the real-time status of each managed component. When **Fixed Content** and **Storage Area** entries display as *Unavailable*, it means the health-probe service cannot successfully query those subsystems. This is almost always a **connectivity or service-availability issue**, not a display bug in the page itself.

## Most Common Causes & Fixes

### 1. Content Engine services not running / crashed
- Verify that the CStore, PSS (Process Scanning Service), and any Fixed Content Device agent services are **up and running**.
  - *Linux/UNIX:* `ps -ef | grep cpe` or `systemctl status <service>`
  - *Windows:* Services console → look for Content Engine–related services.
- Restart any stopped or hung services.

### 2. Fixed Content Device (FCD) unreachable
- The FCD (e.g., a NetApp NFS/CIFS share, database-backed store, or object store) is **down or unreachable over the network**.
  - Test connectivity: `ping`, `nslookup`, `nc -zv <fcd-host> <port>`.
  - For NFS: confirm the export is mounted (`mount | grep <path>`) and the NFS client is running.
  - For CIFS/SMB: confirm the share is accessible and credentials in the Content Plugin are still valid.
- Check for DNS failures or firewall rules introduced by a recent change.

### 3. Storage Area misconfiguration or corruption
- The logical **Storage Area** object in the content repository may be in an *error* or *offline* state after a failed migration, disk replacement, or permission change.
- Open the Content Engine admin console → **Storage Areas** tab and confirm the area's status. Reset or re-point the area to a valid physical path if needed.
- Verify disk quotas and free space on the underlying volume (`df -h` / `fsutil volume diskfree`).

### 4. Certificate / SSL or authentication expiry
- If the health probe uses HTTPS or mutual-TLS to reach the FCD, an **expired or missing certificate** will cause the probe to fail, and the page will mark the item "unavailable."
- Rotate/renew the certificate and re-deploy it to the trust store.

### 5. Database connectivity
- The metadata repository (DB2, Oracle, SQL Server) that stores the Storage Area definitions may be unreachable.
  - Confirm DB listener is up, JDBC/ODBC connectivity string is correct, and the CPE connects successfully.

### 6. Stale cache / page rendering
- Occasionally the health page caches a prior error state.
  - **Clear the browser cache / hard-refresh** (Ctrl+Shift+R).
  - Restart the Content Engine web tier (`httpd`/`APC`/`Tomcat` container) so the health service re-queries all components.

## Step-by-Step Triage

1. **Check services** – Ensure all CE services are running on every node.
2. **Test FCD connectivity** – Ping / port-check / mount-verify the Fixed Content backend.
3. **Inspect Storage Area status** in the admin console; look for error codes in the CE log (`CPE_FCD.log`, `cstore.log`, `system.log`).
4. **Validate credentials & certificates** used by the Content Plugin / FCD agent.
5. **Confirm DB reachability** from each CE node.
6. **Restart the web/admin tier** to force a fresh health poll, then reload the System Health page.
7. **Review logs** for timestamps that correlate with when the "unavailable" status first appeared – this pinpoints the failing component.

## Prevention

- Enable monitoring/alerting on FCD reachability and Storage Area status (SNMP trap or syslog forward to your ITSM/monitoring stack).
- Schedule periodic certificate and credential rotation.
- Keep CE patches (IFIX / interim fix) current to avoid known health-probe bugs.

If the page still shows *Unavailable* after all backend services are confirmed healthy and reachable, capture the CE log files around the failure timestamp and open a support case with the vendor's Content Engine team.

# Importing a Certificate in ITCAM for Data Power

To import a certificate into the **ITCAM Agent for Data Power** (BN Agent), use the Java `keytool` command on the host where the ITCAM agent runs.

## Steps

1. **Prepare the certificate file**
   - Use either a `.cer` or `.pem` file.
   - Confirm the file is in **ASCII** format, **not binary**.

2. **Run the `keytool` import command**

   ```bash
   <ITM_ROOT>/JRE/<jre_version>/bin/keytool -import -trustcacerts \
     -alias <unique_alias_name> \
     -keystore <ITM_ROOT>/JRE/<jre_version>/bin/lib/security/cacerts \
     -storepass <keystore_password> \
     -file <path_to_certificate_file>
   ```

   **Concrete example:**
   ```bash
   /usr/ITM/JRE/aix526/jre/bin/keytool -import -trustcacerts \
     -alias ligitalsso \
     -keystore /usr/ITM/JRE/aix526/jre/bin/lib/security/cacerts \
     -storepass <fileName> \
     -file /NEWSSL-sscert.cer
   ```

### Parameter summary

| Parameter | Purpose |
|---|---|
| `-import` | Import the certificate |
| `-trustcacerts` | Trust the CA certificate (adds it to the trust store) |
| `-alias <name>` | A unique identifier for the certificate within the keystore |
| `-keystore <path>` | Path to the JRE's default `cacerts` trust store |
| `-storepass <pass>` | Password for the keystore (JRE default is typically `changeit`) |
| `-file <path>` | Full path to the `.cer` or `.pem` certificate file |

3. **Restart the ITCAM Agent for Data Power** so the new certificate takes effect.

## Important Notes

- The `<ITM_ROOT>/JRE/<jre_version>` path must point to the **JRE bundled with ITCAM**, not a system-wide Java installation.
- If you are doing this over an HTTPS management connection, a missing or mismatched CA certificate on the agent side will produce errors such as:
  `javax.net.ssl.SSLHandshakeException: Received fatal alert: handshake_failure`
  Importing the correct CA/server certificate resolves this.
- You can verify the import succeeded by listing the keystore contents:
  ```bash
  <ITM_ROOT>/JRE/<jre_version>/bin/keytool -list \
    -keystore <ITM_ROOT>/JRE/<jre_version>/bin/lib/security/cacerts \
    -storepass <storepass> | grep <alias>
  ```
